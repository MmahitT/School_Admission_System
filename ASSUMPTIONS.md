# ASSUMPTIONS

Final. Every point the assignment left open, with **what** was assumed, **why** it was necessary and **how** it was implemented. Items marked *Approved* were put to the project owner explicitly (decisions D1–D5 and the environment-setup decision) and confirmed.

| ID | Topic | Assumed | Why necessary | Implementation |
|---|---|---|---|---|
| A1 | Admin access without login | The admin UI (`/admin`) and `POST /classes` are open to anyone who can reach the app. | Spec forbids a login system. | Separate `/admin` route with a clear "Admin (no authentication — demo)" banner; header switch between Parent/Admin views. Documented as non-production. |
| A2 | Identifiers | Class and hold IDs are UUID strings, not the `c_123`/`h_789` shown in the spec examples. | DB spec mandates UUID PKs; examples read as illustrative. | UUIDs serialized as lowercase strings. |
| A3 | Student identifier | Exactly 17 ASCII digits `^[0-9]{17}$`; no trimming of internal spaces; leading/trailing whitespace is rejected by the API (FE trims before send). No checksum/year validation. | Spec defines only length and digits. | The same rule in three places: the frontend form (React Hook Form validation, surrounding spaces trimmed first), the API (`StudentId.IsValid`, `^[0-9]{17}$` so only ASCII digits pass), and a database CHECK. HTTP itself strips leading/trailing spaces from header values. |
| A4 | Class/shift | One `AdmissionClass` row = one class+shift combination, named freely. Names are unique case-insensitively. Seats cannot be edited or classes deleted (no such endpoint). | Spec defines create/read only; duplicates would confuse parents. | Unique index on `lower(name)`; duplicate → 409 `DUPLICATE_CLASS_NAME`. |
| A5 | Hold duration | Default 600 s, from `HOLD_DURATION_SECONDS`; must be a positive integer, otherwise the app fails fast at startup. Read once at startup. | Spec requires configurability. | `AdmissionOptions` bound from env. |
| A6 | Duplicate application policy | A student may have at most one application per class in status HELD, CONFIRMED or CANCELLED. An **EXPIRED** application does **not** block applying to the same class again. A student may hold only one HELD application at a time across all classes. A student with a CONFIRMED admission may still apply elsewhere (spec does not forbid it). | Spec text conflicts: "same class more than once, including after confirmation or cancellation" vs. "apply again" after expiry. EXPIRED is the only status omitted from the list, so it is treated as the retryable one. | Partial unique indexes (see PROJECT_SPECIFICATION §4). *Approved (D2).* |
| A7 | Expiration | A HELD row with `expires_at <= now` is treated as expired everywhere (counts, reads, confirm) regardless of whether the sweeper has run. The sweeper (every 5 s) persists `EXPIRED`. | Spec: correctness must not depend on the sweeper's timing. | Time predicate in every query + lazy expiry in write paths + `BackgroundService`. |
| A8 | Payment simulation | "Pay Admission Fee" always succeeds; no amount, no card data, no payment table. | Spec: simulated payment only. | Dialog labelled "Simulated payment" → `POST /holds/{id}/confirm`. |
| A9 | Cancellation | Only the owner may cancel; only HELD (non-expired) holds are cancellable; cancelling an already CANCELLED hold returns 204 (idempotent); CONFIRMED/EXPIRED → 409. A cancelled hold still blocks re-applying to that class (A6). | Spec silent on repeats. | `HoldService.CancelAsync`. |
| A10 | Ownership errors | Wrong `X-Student-Id` on confirm/cancel → 403. `GET /holds/{id}` is readable without the header (per spec) and exposes no student id. | Spec requires ownership verification but no status code. | Check in service layer. |
| A11 | Time zone | All timestamps stored as `timestamptz` in UTC and serialized as ISO-8601 with `Z`. UI shows local time for display only. One backend instance; clock via injected `TimeProvider`. | Spec: UTC consistently. | Npgsql UTC-only DateTime handling; `TimeProvider.System`. |
| A12 | API error structure | RFC 7807 problem details (`title`, `status`, `detail`) plus a stable machine-readable `code` and a `traceId`. Status mapping: 400 invalid input, 403 not the owner, 404 not found, 409 business conflicts, 500 unexpected only. **422 is deliberately unused** (all input validation is 400). | Spec requires meaningful 4xx errors but no format. | `GlobalExceptionHandler` (`IExceptionHandler`); `AdmissionException` carries kind + code. *Approved (D5).* |
| A13 | Polling | Classes and my-applications refetch every 5 s while the tab is visible; countdown ticks every 1 s from server `expiresAt`; timers cleaned on unmount. No WebSockets/SSE. | Spec requires periodic refresh; simplest reliable option. | `usePolledResource` hook (fetch immediately, then every 5 s while the tab is visible; timers cleaned on unmount) and `useServerNow` (1 s tick). |
| A14 | Concurrency strategy | Single PostgreSQL primary; per-class `SELECT … FOR UPDATE` in a `READ COMMITTED` transaction; DB constraints/trigger as backstops; no distributed cache or queue. | Spec recommends this approach. | See PROJECT_SPECIFICATION §6. |
| A15 | API routing | Backend serves bare spec paths; nginx exposes them both as `/api/...` and bare paths on :8080. Backend is not published on a host port in compose. | Spec says both `localhost:8080/classes`-style base URL and `/api/classes` via proxy. | `nginx.conf` location blocks. *Approved (D3).* |
| A16 | CORS | Same-origin through nginx in Docker; dev origin (`http://localhost:5173`) allowed via `CORS_ALLOWED_ORIGINS`. | Needed for Vite dev server. | ASP.NET CORS policy from env. |
| A17 | Limited-seats threshold | "Limited seats" = available ≤ 5 or ≤ 10 % of total (and > 0). | Spec names the state but not the threshold. | Pure UI helper, unit-tested. |
| A18 | Data lifecycle | Data persists in the named volume `pgdata`; `docker compose down` keeps it; only `down -v` wipes it. Migrations run automatically on backend start. No seed data: the admin creates classes through the UI. | Spec requirement. | Compose volume + EF `Migrate()` at startup. |
| A19 | Runtime version | .NET 8 (SDK 8.0.403 locally, `dotnet/sdk:8.0` and `aspnet:8.0` images in Docker). Note: .NET 8 LTS reaches end of support on 10 Nov 2026; moving to .NET 10 is a change of `TargetFramework` and the Docker image tags. | Spec allows 8 or newer; 8 was the SDK available for local build and test. | `*.csproj`, `backend/Dockerfile`. *Approved (D1).* |
| A20 | Input limits | Class name ≤ 200 characters; total seats ≤ 100,000. | Unbounded input is a validation hole; spec only requires "> 0". | `ClassService` validation (400 `VALIDATION_FAILED`). |
| A21 | Connection pool | Npgsql pool capped at 50 connections with a 30 s wait, unless the connection string sets them. | 1,000+ simultaneous requests must queue inside the app rather than exhaust PostgreSQL's 100 connections or time out at the 15 s default. | `AddInfrastructure`. |
| A22 | Malformed input | Bad JSON, wrong types, or a non-GUID id in the path → 400 `VALIDATION_FAILED` (never 500). | Spec: no 500 for validation errors. | `InvalidModelStateResponseFactory`. |
| A23 | Expired hold on confirm/cancel | Confirming or cancelling a time-expired HELD hold marks it EXPIRED (committed) and returns 409 `HOLD_EXPIRED`. | Spec: expired holds must never be confirmed, and must not remain HELD past expiry. | `HoldService` returns an outcome so the EXPIRED write commits before the error is raised. |
| A24 | Server-time countdown | The browser learns the server/browser clock offset from the HTTP `Date` header of each API response (centred within its 1-second truncation) and counts down to the server's `expiresAt`. Displayed time is floored to whole seconds. When the countdown reaches zero the UI shows EXPIRED, disables payment, and immediately re-fetches the authoritative status. | Spec: the countdown must use the server's `expiresAt`, not a purely local timer. | `utils/serverClock.ts`, `api/client.ts`, `MyApplications`. Accuracy ≈ ±0.5 s; the backend never relies on it. |
| A25 | Apply-button hints | The UI disables Apply when the class is full, when the student already has an active hold, or when their application to that class is HELD/CONFIRMED/CANCELLED. These are hints only; the backend still enforces every rule and its errors are shown if the UI state was stale. | Better UX without making the frontend the source of truth. | `ClassCard`, `ClassList`. |
| A26 | Placeholder school identity | School name "Bright Future School" and a generic logo icon are placeholders. | Spec requires a logo placeholder and school name but gives none. | `layouts/AppLayout.tsx`. |
| A27 | Expiration sweeper | `HoldExpirationService` sweeps every `EXPIRATION_SWEEP_INTERVAL_SECONDS` (default 5), once immediately at startup (catch-up after downtime), with one atomic `UPDATE … WHERE status='HELD' AND expires_at <= now`. A failed sweep is logged and retried at the next interval. It is a normalizer only: reads, allocation, confirm and cancel already treat time-expired holds as expired. `DisableExpirationSweeper=true` (config) turns it off; used only by tests. | Spec: automatic expiry via a hosted service, without correctness depending on its timing. | `Infrastructure/BackgroundServices/HoldExpirationService.cs`. |
| A28 | Secrets and required configuration | The database password is never hard-coded or defaulted anywhere. `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` are required: Docker Compose refuses to start without them, `.env.example` ships with an **empty** password, and `.env` is git-ignored. The backend additionally validates its configuration before building any service (connection string complete, durations positive, CORS origins explicit) and exits with a message that names the problem but never prints a value. As a consequence `docker compose up --build` fails on first run until `.env` is created and the password set, and `docker compose down` also needs the `.env`. | Security was prioritised over first-run convenience; the alternatives (a default password in the compose file, or a committed `.env`) would put a credential in the repository. | `docker-compose.yml` (`${VAR:?message}`), `EnvironmentValidator`, `.gitignore`, README Quick start. *Approved (Option 1).* |
| A29 | Password characters | The password is placed in a PostgreSQL connection string, so it should contain letters and digits only (`openssl rand -hex 24`). | `;`, `=` and quotes are connection-string syntax. | Documented in `.env.example` and the README; the startup validator reports a malformed connection string without echoing it. |
| A30 | Browser-side exposure | Only `VITE_*` variables are compiled into the frontend, and the frontend container is given only `VITE_API_BASE_URL` (`/api`, public by design). | The browser must never receive credentials or backend settings. | `docker-compose.yml` build args; `scripts/security-check.sh` verifies the running container and the files nginx serves. |
| A31 | HTTP hardening | nginx sends a strict `Content-Security-Policy` (scripts from self only; `unsafe-inline` for **styles** only, needed for React inline style attributes), `X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and hides its version. No HSTS or TLS: the deployment is plain HTTP on localhost. | Cheap defence in depth for a public-facing page; TLS termination is an infrastructure concern outside the assignment. | `frontend/nginx.conf`, `frontend/security-headers.inc`. |
| A32 | Scale | A single backend instance. The sweeper and the injected clock are not designed for several replicas; correctness of seat allocation does not depend on that (it is enforced by the database), but the background sweep would run once per replica. | Spec describes one deployable unit. | Documented in README limitations. |
